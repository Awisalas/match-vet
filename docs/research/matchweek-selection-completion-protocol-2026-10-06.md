# Selection completion: SQLite and Python source findings

Research date: 2026-10-06. Scope: official SQLite and Python documentation, read-only inspection of this repository, and a read-only clock availability query on the current Android/Termux host. These findings specify what a repository-local post-commit acknowledgement can prove; they do not treat a timestamp stored before a commit as proof that the commit finished before the timestamp.

## Commit and durability

- SQLite transactions are atomic across process, operating-system, and power failure under SQLite's documented storage assumptions. In WAL mode, a commit record appended to the WAL is the logical commit point; only one WAL writer operates at a time. A checkpoint is separate from commit. The WAL file is part of persistent database state and must accompany the database until safely checkpointed. Sources: [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html), [SQLite WAL](https://www.sqlite.org/wal.html).
- `PRAGMA synchronous=FULL` in WAL mode synchronizes the WAL after **each transaction commit**. SQLite describes WAL plus `FULL` as durable across power failure. WAL plus `NORMAL` remains consistent but can lose the most recent committed transactions after power or OS failure; it is therefore insufficient for an acknowledgement whose later survival must prove that the selected row was durable. Application-process crashes alone do not require `FULL` for committed data to survive. Source: [SQLite synchronous pragma](https://www.sqlite.org/pragma.html#pragma_synchronous).
- In rollback-journal `DELETE` mode, `FULL` can lose a transaction after power failure because the journal deletion's directory entry may not be synced. `EXTRA` adds that directory sync. The existing store's WAL plus `FULL` profile avoids this particular gap; switching journal mode requires reassessing the proof. Sources: [SQLite synchronous pragma](https://www.sqlite.org/pragma.html#pragma_synchronous), [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html).
- SQLite's durability model assumes the VFS and filesystem truthfully implement its synchronization and locking operations. SQLite explicitly documents the `flush`/`fsync` assumption and that broken implementations can defeat recovery. `FULL` is therefore a conditional storage guarantee, not a proof against lying hardware, rogue file writers, or arbitrary filesystem corruption. Sources: [SQLite atomic commit, assumptions and limitations](https://www.sqlite.org/atomiccommit.html), [SQLite VFS](https://www.sqlite.org/vfs.html).
- A failed `COMMIT` cannot be acknowledged as successful. SQLite documents that `COMMIT` can return `SQLITE_BUSY` and leave the transaction active; transaction state must be handled before any capability is issued. Source: [SQLite transaction](https://www.sqlite.org/lang_transaction.html).

## Python transaction boundary

- The repository opens its writer connection with `isolation_level=None`, explicitly executes `BEGIN IMMEDIATE`, and invokes `Connection.commit()` on normal exit from `Store.transaction()` (`src/matchvet/store.py:4353-4366`, `4908-4912`). Under Python's documented legacy transaction handling, `isolation_level=None` prevents **implicit** transaction opening but permits explicit SQL transactions. `Connection.in_transaction` reflects the low-level SQLite transaction state. Source: [Python sqlite3 transaction control](https://docs.python.org/3/library/sqlite3.html#transaction-control-via-the-isolation-level-attribute).
- `Connection.commit()` commits a pending transaction. With `autocommit=True`, it has no effect; and with no pending transaction, a context manager does nothing on exit. Consequently an acknowledgement must follow the successful exit of this repository's explicit selection transaction and its verified mutation, not an arbitrary `commit()` call or a clock read inside the transaction. Source: [Python sqlite3 Connection methods and transaction control](https://docs.python.org/3/library/sqlite3.html), [Python sqlite3 connection context manager](https://docs.python.org/3/library/sqlite3.html#how-to-use-the-connection-context-manager).
- A post-return repository clock sample `t_ack < T` is an upper bound on the SQLite selection commit's completion, provided the executing process has not been allowed to construct an acknowledgement by any other path. Selection can become physically durable before `commit()` returns; a crash in that interval leaves an orphan selected row with no valid acknowledgement. That row must remain unqualified. This is a deduction from the documented commit and synchronization ordering, not a SQLite timestamp feature. Sources: [SQLite synchronous pragma](https://www.sqlite.org/pragma.html#pragma_synchronous), [Python sqlite3 transaction control](https://docs.python.org/3/library/sqlite3.html#transaction-control).

## Time source and the receipt's actual claim

- Python's `time.time()`/`time.time_ns()` gives wall time; `CLOCK_REALTIME` can be changed. Python's monotonic clocks cannot go backwards due to a wall-clock update, but their origin is undefined, so a monotonic reading alone cannot be compared with a UTC cutoff. On Linux, `CLOCK_BOOTTIME` is monotonic and includes system suspension; `CLOCK_MONOTONIC` excludes suspend time. Source: [Python time module](https://docs.python.org/3/library/time.html).
- The current host reports Python 3.14.6, SQLite 3.53.3, and `time.CLOCK_BOOTTIME` available; `time.monotonic()` uses `CLOCK_MONOTONIC`, and `time.time()` uses adjustable `CLOCK_REALTIME` (read-only `python` clock query on 2026-10-06). These observations establish API availability, not clock accuracy or resistance to clock rollback.
- To assert a UTC `T`, the repository must trust an accurate, nonrollback UTC clock at the post-commit sample (or a trusted UTC anchor plus elapsed time that includes suspension, under a stated reboot/anchor policy). If the wall clock can be stepped backward after real `T`, a locally produced `t_ack < T` can be false in real UTC. If stepped forward before `T`, the result is conservative refusal. Monotonicity can detect or limit some local discontinuities but cannot independently establish an absolute UTC deadline. This is a deduction from Python's clock contracts. Source: [Python time module](https://docs.python.org/3/library/time.html).
- A receipt persisted after `T` can attest to the earlier, pre-`T` **selection commit return** without any requirement that the receipt itself committed before `T`: it records the result of a trusted live program path that sampled time only after successful selection commit return. This breaks the apparent final-write regress because the later receipt's own publication time is not the qualifying event. It is an application trust claim, not a cryptographic timestamp. A database row by itself cannot prove that no privileged actor forged or backfilled it; the protocol must enforce private, unforgeable-in-process, one-use authority and prohibit restart reconstruction. If hostile operators, memory dumps, or arbitrary store modification are in scope, a separate trust anchor or witness is required. These are protocol deductions, not guarantees supplied by SQLite or Python.
- A pause after commit return but before the clock read can push `t_ack` to `T` or later, requiring refusal. A pause after a valid `t_ack < T` can push receipt persistence past `T` without changing the already established ordering. The in-memory authority must be bound to its creating process and operation, invalidated on fork or process exit, and never serialized. Neither a new process nor a reopened store in the same process may reconstruct it from the selected row. These are necessary protocol rules, not properties automatically provided by SQLite or Python.

## Consequences for recovery

- Selection commit returned before `T`, then process crashes before receipt persistence: WAL `FULL` preserves the selected row under the stated storage assumptions; absence of the receipt forces permanent refusal for that logical Matchweek. Selection must remain single-assignment so recovery cannot choose another candidate. The same applies if the process crashes after its clock sample or while the receipt is being committed, unless a complete, valid receipt survives recovery. A receipt transaction that becomes durable despite no return from its own `commit()` is acceptable if its issuance was already authorized by the earlier pre-`T` acknowledgement. This is a protocol deduction from the commit ordering above.
- If the selection commit did not return successfully, no live completion capability is issued. Recovery may find an orphan selection that had committed physically before the interruption; it remains unqualified. A receipt without the exact immutable selection and intact reference graph is invalid. At `t_ack == T`, qualification fails because the required comparison is strict. These are protocol requirements rather than SQLite behavior.
- The existing generic `ArtifactStore.publish_manifest()` samples `verified_at_utc` before object/catalog persistence (`src/matchvet/artifacts.py:637-712`), so that field cannot attest to a post-selection `commit()` return. However, the current `SnapshotManifest` and catalog already have immutable `UNIQUE(snapshot_id)` assignment, `matchweek_id`, `research_cutoff_id`/`research_cutoff_utc`, `parent_snapshot_id`, exact artifact references, version references, and `created_at_utc` (`src/matchvet/artifacts.py:172-303`; `src/matchvet/store.py:353-436`). Two domain-restricted manifests could represent selection and subsequent receipt: deterministic selection/receipt snapshot IDs for the logical Matchweek; receipt parent and artifact reference naming the exact selected manifest; repository-assigned post-commit time in receipt `created_at_utc`; protocol and policy identities in existing version references. Under that representation, **no SQLite schema or manifest JSON migration is inherently required**. This is a local schema observation, not a claim that the current public API already enforces the protocol.
- Existing publication is insufficient without narrow repository hooks and namespace protection. `publish_manifest()` accepts caller-authored `created_at_utc`, has an idempotent existing-snapshot return path, and can publish arbitrary snapshot identities; a generic caller could therefore fabricate or backfill a receipt after restart if allowed into the reserved selection/receipt namespace (`src/matchvet/artifacts.py:592-712`). The protected path must reserve those deterministic identities, reject generic publication into that namespace, distinguish a **fresh** selection commit from an idempotent lookup, sample the trusted clock only after that commit returns, and allow receipt publication only from the still-live one-use authority. Recovery must verify the complete receipt/selection/reference graph. These are application requirements; SQLite alone does not enforce them.
